1. One request, five steps (same in both servers): (1) the request arrives over HTTP; (2) its text becomes tokens; (3) the server looks for KV cache it can reuse. This is the only step the figure shows as different: vLLM matches hashed full blocks, SGLang matches a prefix in a radix tree. This is a simplification, because both projects now cache shared prefixes; (4) it computes only the part that is not cached; (5) it sends one token at a time, and the batch is refilled after every step.
2. Batching (iteration-level scheduling, often called continuous batching; both servers do it). After each forward step, finished requests leave and waiting requests join. Example with three slots over four steps: A (slot 1) leaves after step 2 and D takes the slot; B stays all four steps; C (slot 3) leaves after step 3 and E takes the slot. The GPU does not wait for the slowest request.
3. Same prompt start, three requests (illustrative). vLLM stores the cache in fixed-size blocks, like OS memory pages. Each full block is hashed from its tokens and its parent block's hash. Request 1 computes blocks B1-B3 plus its own block (label "computes"); requests 2 and 3 reuse B1-B3 and add their own block (label "reuses"). An optional per-request cache salt keeps users' caches apart. SGLang's RadixAttention keeps the cache of shared prefixes in a tree: root, then one "shared prompt" node, then one own branch per request. There is one stored copy of the shared start.
